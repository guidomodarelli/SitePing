---
title: Screenshots
description: Capture the annotated area as an image — with privacy masking and region metadata.
---

With `enableScreenshot: true`, the widget captures a JPEG of the area around each annotation when the client hits Send. Your triage view then shows exactly what they saw — including transient states like open dropdowns or hover styles that a later visit can't reproduce.

```ts
initSiteping({
  endpoint: "/api/siteping",
  projectName: "my-project",
  enableScreenshot: true,
});
```

## What gets captured

- The drawn rectangle **plus generous context** around it (up to ~280 px horizontally, ~220 px vertically), so the screenshot is recognizable, not a postage stamp.
- Rendered at the device's pixel ratio, encoded as JPEG (quality 0.85), downscaled when wider than 1200 output pixels — on a 2× display that's about 600 CSS pixels of page width.
- A `screenshotRegion` — the annotation's position inside the image as fractions — travels with it, so dashboards can re-draw the rectangle on top of the screenshot.
- Captured **once** per submission and reused across retries.

## Privacy masking

Add `data-siteping-ignore="true"` to any element that must never appear in a screenshot. The element and all its descendants are removed from the render:

```html
<div data-siteping-ignore="true">
  <CreditCardForm />
</div>
```

The value must be exactly `"true"` — the bare attribute or `"false"` does not mask. The widget's own UI opts out the same way, so screenshots never contain SitePing chrome.

> Masking an element also disables [right-click commenting](/docs/widget/right-click) on it — the widget treats `data-siteping-ignore` as "not mine to touch".

## Failure is always safe

Screenshot capture is best-effort by design: if the rendering engine fails to load or the capture throws, the feedback **still submits** — just without an image. A screenshot problem never loses a client's comment.

## Where the image goes

By default the JPEG travels inline (a `data:` URL, capped at 1.5 MB) and is stored as-is by the adapter. That's fine to start; for production volume, configure a [`screenshotStorage`](/docs/adapters/prisma#screenshot-storage) on the server adapter to upload images to S3/R2/GCS and store only the URL.

`@beezping/screenshot-storage` provides that `screenshotStorage` ready-made: wrap a backend — `/cloudflare-images`, `/s3` (AWS S3, Cloudflare R2, Backblaze B2, MinIO…), `/drizzle-pg` and `/drizzle-libsql` (your own PostgreSQL or Turso/libSQL database, through Drizzle), `/filesystem` (Node.js), `/memory`, or your own `ScreenshotObjectStore` — with `createScreenshotStorage` and pass the result to your store. It validates the image type and size before any upload (`maxBytes` must be a positive integer, checked when the storage is created; active formats such as `image/svg+xml` are refused, and every served screenshot is sandboxed with `Content-Security-Policy: default-src 'none'; sandbox`), stores each screenshot under a fresh random key (one URL per upload, never shared between feedbacks), and serves backends without a public URL through `createScreenshotServeHandler` (cached as `public, immutable`, or `private, no-cache` when you pass an `authorize` callback: shared caches never bypass it, and the browser revalidates every reuse — answered with a cheap `304` — so a logout or revoked access applies at once). `delete` only removes keys it generated (its `keyPrefix` plus the random-key shape), never another object behind the same bucket or CDN (a URL with malformed percent-encoding counts as not its own, so a corrupt record never makes `delete` throw); likewise the serve handler only serves keys under its own `keyPrefix` (pass it the one you gave `createScreenshotStorage`; both default to `siteping-`), so apps sharing a directory or bucket cannot read each other's screenshots, and `authorize` receives the requested key.

On S3 with least-privilege credentials — an IAM policy granting `s3:GetObject`, `s3:PutObject` and `s3:DeleteObject` but not `s3:ListBucket` — a missing key comes back as `403 AccessDenied` instead of `404`. Pass `treatAccessDeniedAsMissing: true` to `createS3ObjectStore` so the serve handler answers `404` for it rather than `500`; only the `AccessDenied` code is mapped, so credential failures (`SignatureDoesNotMatch`, `InvalidAccessKeyId`, `ExpiredToken`…) still fail. It is off by default: it would also hide a policy missing `s3:GetObject` behind `404`s.

An upload that times out may still land after SitePing gave up: the key is removed at once and again after `uncertainUploadReclaimDelaysMs` (5 s, 30 s, 2 min by default; with the default timer, each delay must stay under about 24.8 days — 2,147,483,647 ms — unless you pass your own `scheduleReclaim`). Those retries live in process memory, so on serverless platforms also pass `onUncertainUpload` to enqueue the key in a durable job, or add a lifecycle rule on the bucket for objects under `keyPrefix`.
